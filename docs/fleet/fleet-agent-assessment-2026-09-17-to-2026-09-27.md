## Executive assessment

The network produced substantial **engineering activity**, but work control and outcome verification are not keeping pace. In the exact window, GitHub shows **36 PRs opened under `bshelby88`: 21 merged, 4 closed without merge, and 11 still open**. Airtable added **222 work records**, yet its 633-record queue has **435 queued, 10 blocked, and 188 completed, with no `in_progress` state represented**. Of 3,674 heartbeat events, 3,673 are service/liveness-bridge events; only one is a `working` event for Kip. The ten session records found for the window are daily fleet-health reports, not task-completion journals.

The evidence supports a **high-output / low-closure** assessment. There are useful service fixes, discovery work, a live API, and repeated health monitoring. But the current evidence does not support claims that campaign activity equals execution, that health checks prove paid-service readiness, or that a responsive agent endpoint proves an agent completed work. RAEN itself records **$0 external revenue and zero revenue events**. A separate $0.02 USDC transfer was independently found on-chain; it is an internal validation/settlement action, not customer revenue. More seriously, Commerce Reconciliation has one `$0.01` row marked recognized even though its linked transfer is outgoing from the RAE wallet and the row has no order, capture, customer-identity, or recognition-basis evidence. **No substantiated customer revenue was established; the ledger flag requires finance review.**

**Risk posture: RED before further unattended money movement or agent dispatch.** The highest priorities remain the RAEN engine's automatic signing path, the trust-based revenue middleware, and the fragmented/non-durable job execution path. The local AEK source also has unauthenticated webhook/action handlers that synthesize `DELIVERED`/`RELEASED` outcomes, and can mark a staged-only dispatch as verified completion. These are source-level deployment gates; parity with the running image is not established. No communications path reliably proves that a task was accepted, executed, and returned with independently verified evidence.

## Project and platform findings

### P0 — RAEN can sign an internal transfer on every funded tick

`run_single_tick()` calls `attempt_settlement_if_funded()` on each engine iteration; if the payer has at least $0.02, it calls `run_facilitator_settle()` (`src/engine.py:97-135`). That method loads a payer key and invokes `settle_on_chain()` for $0.02 to the configured treasury (`src/settlement.py:56-66,148-176`). The chain/explorer record confirms one successful $0.02 transfer. The loop has no visible invoice/customer gate, per-run approval, spend cap, or once-only guard. The first-sale gate is a separate revenue-classification check and does not authorize the send (`src/first_sale.py:63-153`).

**The engine's own metrics are inconsistent:** 11 ticks in state; the latest tick log reports 195 campaigns; state reports 221; `campaign_log.jsonl` contains 247 rows, all `LOGGED`; `revenue_events.jsonl` has zero rows. The dispatcher explicitly writes `status: LOGGED` and then increments `campaigns_executed` (`src/kernel.py:134-145`). `log_settlement_result()` writes a log line but does not update settlement state (`src/kernel.py:181-183`), while the state says no last settlement attempt. The word “executed” therefore overstates campaign work, and the settlement status display can be stale. Latest recorded engine state is 2026-09-27 04:19Z; no active-loop state was verified at the audit cutoff.

**Gate:** do not restart unattended RAEN until signing is disabled by default or individually human-authorized, bounded, idempotent, and independently tested.

### P0 — Tiffany revenue-server payment proof is spoofable; verifier fallback is fail-open

`fleet/x402-payment-middleware.js:27-68` defaults the treasury to the zero address and trusts client-supplied `x-payment`/`x-payment-tx`/amount fields; it labels the on-chain check “simplified” and grants access when the claimed amount meets price. `tiffany-revenue-server.js:16` imports that middleware. Its test uses fabricated transaction identifiers (`test/revenue-server.test.js:149-153,229-252`); **17/17 tests passed**, but those tests demonstrate the spoof path rather than prove settlement. `package.json:6-10` wires `npm test` only to an import smoke check.

A newer `x402-payment-verifier.js` exists but defaults `allowFallback = true` and falls back to trusting the same headers when RPC/viem is unavailable (`:19-21,59,379-387,446-471`). Its existence does not repair the server. The Fly config names `tiffany-revenue-server` and sets the zero treasury (`fleet/fly.toml:5,31-34`), but an exact live Fly status query returned “Could not find App.” This is a **pre-deployment blocker**, not evidence that the vulnerable server is currently serving traffic.

Even a successful local payment gate would not prove product fulfillment or durable accounting: the paid handlers return random/canned data (`tiffany-revenue-server.js:59-125`), and the server appends to an in-memory tracker (`:20-22,39-54`). The separate SQLite `revenue-store.js` is not imported by this server, and its Fly config declares no persistent volume (`revenue-store.js:37-74,90-120`; `fly.toml:11-16`).

Other local billing prototypes are also unsafe if mounted: `api-auth.js` stores full API-key strings and its `listApiKeys()` returns those values (`fleet/api-auth.js:65-90,112-124`); `royal-ruby-saas-routes.js` returns active subscription records without authorization (`:210-220`). The inspected Tiffany server does not import these modules (`tiffany-revenue-server.js:15-24`); their exposure in any other entrypoint was not established, so treat them as pre-deploy blockers rather than confirmed live exposures.

### P1 — AEK runtime accepts work but is not a durable worker queue

The README claims separate API and worker Fly process groups plus managed Postgres (`rae-aek/rae-aek-v0.4/README.md:3-12`). The deployed `rae-kernel` has two started 256 MB `app` machines and no Fly volume; `/readyz` reports `database: sqlite`, 17 work items, 15 queued, 2 completed. The local default is SQLite (`app/database.py:7-8`), and `fly.toml` declares only `processes = ["app"]` (`:16-18`); the worker loop exists in `app/worker.py:4-12` but is not a deployed process. Thus the live API is healthy while almost all of its queue is waiting and state is not backed by managed Postgres/shared durable storage.

Fleet dispatch is explicitly staged/disabled: `/v1/fleet/dispatch` returns `outbound_delivery_enabled: false` (`app/main.py:170-178`), and tests assert dispatch work is blocked (`tests/test_fleet.py:95-109`). The outbound HMAC helper is not called by the production app/worker path; the only discovered call is a unit test (`app/dispatcher.py:15+`, `tests/test_delivery_and_lease.py:26-28`). This is a safe refusal, but not an operational agent dispatcher. Local `python -m pytest -q` could not run because pytest is not installed; no dependency installation was attempted. The AEK branch is 56 commits ahead and has local modifications/untracked modules/tests, so deployed/source parity is also unproven.

**Queue completion is not fenced.** `execute_work()` accepts both queued and reserved records and overwrites `reservation_owner` without checking that the caller owns the reservation (`app/service.py:39-56`). `update_work()` writes by ID with no expected-state/owner compare-and-swap; expiry recovery requeues only `reserved` work, not crashed `executing`/`verifying` work (`app/repository.py:29-50`); the worker invokes only that limited recovery before `run_next()` (`app/worker.py:4-10`). The dead-letter queue is an in-memory singleton, is not connected to the repository/worker, and its instance listing methods omit `self` (`app/deadletter.py:22-26,67-79`). Exclusive execution, crash recovery, and durable retries are not demonstrated.

**A staged dispatch can be reported as verified completion.** The `fleet.dispatch.stage` capability returns `staged: true` even when `dispatch_enabled` is false (`app/capabilities.py:27-34`); the generic verifier treats that as passed (`:40-43`). `execute_work()` then stores `state=completed` and `economic_outcome.verified=true` (`app/service.py:61-75`), although `/v1/fleet/dispatch` explicitly says outbound delivery is disabled. That is local bookkeeping, not recipient acknowledgement or completed agent work.

### P0 before exposing/redeploying — AEK webhook/action handlers can mint false outcome receipts

In the local source, `/v1/webhooks/inbound-email` has no API-key/signature dependency (`app/main.py:235-246`), and `/v1/webhooks/stripe`, `/v1/escrow/create`, `/v1/escrow/release`, and several other action routes are declared without `require_api_key` (`app/main.py:261-295`). The Stripe handler accepts caller-supplied event/customer/product/amount fields and returns `DELIVERED` without Stripe signature or payment verification (`app/stripe_webhook.py:7-40`). These responses must not be treated as actual fulfillment or settlement. Live exposure and deployed-image parity were not verified; gate these routes before any public exposure or redeploy.

## Intensive job and communications protocol review

There is no single active protocol across Airtable, AEK, HMSDP file jobs, Chronicle handoffs, Hermes cron, GitHub PRs, and Fly health monitoring:

- **Airtable** is the only evidenced current central queue, but it lacks owner/lease/verification coverage and no `in_progress` state. `COMMS-002` (reliable Bryant↔fleet alerting) is itself blocked with no owner or next action.
- **AEK** has a typed work-state model, but its enum has no delivered/acknowledged state (`app/models.py:11-12`); the live deployment is SQLite-only, API-only, with outbound dispatch false. The dispatcher helper signs outbound requests, but the app has no matching HMAC ingress verifier, and HTTP success is treated as delivery (`app/dispatcher.py:10-55`). Queue fencing/recovery, false completion from local staging, and the in-memory broken dead-letter implementation are detailed above. Health verification accepts 200/204 without checking response body/schema/service identity (`app/healthcheck.py:12-24,56-67`); this matches the dated Sep 17 report's false-green echo-stub incident.
- **AEK ingress/action surfaces** in the local checkout are not consistently protected: the inbound-email webhook and Stripe/escrow action routes have no route-level API-key dependency (`app/main.py:235-246,285-295`). Stripe/escrow handlers synthesize delivery/release receipts from caller-supplied fields and do not verify payment or transfer; deployment parity is unknown. The global API key is not per-agent identity (`app/security.py:7-23,26-33`). The Sep 17 morning/evening Chronicle reports also describe an echo-stub false-green, event-store loss during recovery, and scheduler drift; these are dated report claims, not a fresh reconstruction of the underlying run logs (`weekly-report-2026-09-17.md:5,21-25`; `weekly-report-2026-09-17-evening.md:3-5,63-74`).
- **HMSDP** in this workspace is a legacy file broker. The default `G:/My Drive/sprit-mirror` exists, but inspection found only six empty `brain/inbox/{staci,tiffany,agentic,kip,erica,bean}` directories—no `jobs/`, `messages/`, acknowledgements, or queued work. The Python code expects `jobs/{todo,running,done,rejected}` and `messages/{acks,archive}` (`multiAgentic/skills/hmsdp/hmsdp.py:26-62`); the only pending local job file is dated June 28. The current code improves on the older June audit by using `shell=False`, but messages/jobs have no signature, sender authentication, expiry, or replay protection (`:88-140`). Its allowlist checks only the first argument, job `env` is merged into the executor environment, and an uncaught timeout can strand a job in `running` (`:143-203`). The active remote broker/runtime version could not be confirmed.
- **Chronicle handoff** is a Markdown specification with an embedded CLI example, not an installed `scripts/handoff.py` implementation in the checked Chronicle. Its JSON schema excludes `verified` although the lifecycle requires it; the CLI has no `in_progress`, `blocked`, or `rejected` command; `verify_handoff()` compares a caller-supplied string to `expected_result` rather than running the verifier, and it leaves status `completed`. Handoff-file and ledger writes are separate/unlocked, the example contains a forbidden self-handoff, and the canonical-path claim is not implemented (`records/agent-handoff-protocol-2026-09-07.md:46-64,73-84,91-188,204-259,296-309`). The three local handoff JSON records date to Sep 12, outside the audit window, and remain pending.
- **Hermes cron / control plane:** the active local cron directory has no `jobs.json`, and its `executions.db` has zero execution rows. The separate workspace `.hermes/cron/jobs.json` has one `Perpetual Task Discovery` entry (every 30 minutes) and is not the active-profile state. This does not corroborate the dated Sep 19 Chronicle assertion of 39 jobs; archived claims of dual-scheduler drift and fixes are not a current execution history. The Chronicle ledger's latest local entry is Sep 23; the expected `records/work-requests/` directory is absent.
- **A2A/x402** proves only a narrow Sep 19 testnet payment round-trip, not general task/message delivery or commercial mainnet operation. The proof says the v2 stack requires `PAYMENT-SIGNATURE`, while `agents/royal-agentic-enterprises/mcp/x402_settle.py` still sends `X-PAYMENT` (`:2-8,48-52,100-110`); the client also opens a local key file automatically and constructs a signature even in dry mode (`:59-63,85-105`), so do not run it for production without explicit signer authorization. The referenced replay artifacts are absent from the checked workspace. Keep testnet and customer-revenue claims separate.
- **Heartbeats and HTTP health** have no reliable join to an accepted job, execution ID, artifact hash, reviewer, deployment ID, and business outcome. A message written, a status marked completed, or a health endpoint returning 200 is not proof of delivery or completion.

The current safe decision is to keep AEK outbound dispatch disabled and not enqueue more “assigned” work until a canary is demonstrably delivered, acknowledged, and independently read back. A file or Airtable row alone cannot be counted as a task assignment.
